# 08 Foundry Integration & UI

## Targets
Confirm the Foundry and PF2e system versions with the user before building. Use ApplicationV2 for all windows and socketlib for socket relay.

## PF2e adapter
Materials are **real PF2e Items** (treasure/equipment) with module flags (`materialId`, `tier`). All reading of PF2e items, actors, level DCs, and creature level/traits goes through ONE adapter file. A PF2e update should only break that file.

## Permissions and sockets
Players cannot write world settings, scenes, or compendiums. Actions that need those writes (gathering charges on scene tokens, commissions in the world list, exploration scene prep) are relayed to the **active GM client** via socketlib. Hidden rung rolls and loss rolls run there too.

## What a player client loads (Stage 16, v0.16.0)
A player client reads **no definition pack** (both packs are hidden from players' interface, an honor system, not secrecy: see `docs/10`). The GM client sends each player only what their characters need, over one more guarded socket handler, `definitionsFor`.
- **Who is asking.** The handler uses `this.socketdata.userId`, which socketlib fills from Foundry's own socket event (the sender), and ignores the `userId` in the payload. Only a direct call on a GM client (no socketdata) falls back to the payload's id. A GM caller is refused ("The GM client loads every definition itself"). The characters are those the caller owns at Owner level.
- **What is sent.** Recipes the character holds a formula for (own and loaned); blueprints they hold or are designing; materials in their inventory, their Compendium (own, and the party's if they are in the party), an active project's escrow or a queued action; stations in the party's town, in the town of any workshop they own or the party built, named in a saved station state for their characters, or the subject of their upgrade project; the towns those stations stand in; regions whose scene tag is on a scene one of their characters has a token on, or that they are viewing; node types of revealed nodes on those scenes. Plus the resolved output items and `uncraftable` ids for those recipes, and which held formulas have no recipe at all on the GM (`missingRecipes`).
- **What is stripped (Stage 10d, `docs/11b-hub-addendum.md`: nothing a player holds carries a DC, an effect or a percentage).** The player copy of each kind has EXACTLY these fields; it is validated against a strict player schema, so a record that still carried anything else is rejected, and the GM's records are never touched.
  - **recipe**: `kind, id, name, category, baseRole?, slots[{name, drives, tierFloor, qty}], stationCategory, stationTierMin, skillWhitelist, days{default, byStation}`. `days` is worked out on the GM (craft level, the station's craft-day upgrades, the 1-day floor), so the copy needs no `craftLevel`. No `overrides`, `output`, `resultName`, `itemTemplate`, `researchProject`, `craftLevel` or per-slot `lossChance`; the resolved output items are not sent either.
  - **material**: `kind, id, name, tier, value?`. No `effects`, no `lossChance`.
  - **region**: `kind, id, name, sceneTag, skillWhitelist, daysRequired, danger?`. No `spawnTable`, no `explorationDC`.
  - **nodeType**: `kind, id, name, skills, img?`. No `ladders`, no `charges`.
  - **blueprint**: no `researchProject`. Station, town: whole.
  The formula snapshot on the actor no longer carries `craftLevel` either (older snapshots are accepted, then rewritten by the GM's load).
- **What is not sent.** Recipes the character does not hold, blueprints not yet designed (whether the Hub should show a designer a "known to exist" list is an **open Stage 11 question**; nothing is built for it), other regions, other towns' stations, unmet materials, every spawn table and ladder. Corpse yield tables live in token flags, not definitions, so they are not covered by this.
- **When it reloads.** At load, then (debounced 300 ms, and only if the facts that decide the set changed, or the GM's revision changed) on: an owned character's formulas, blueprints, projects, queue, Compendium, stations or location flag changing; a character's ownership changing; a material item created or deleted on an owned character; the user's character changing; a scene's flags, the viewed scene, or tokens changing; the party location, station state, party workshops, shared Compendium or `definitionsRevision` settings changing; a GM connecting. `definitionsRevision` is a world setting the GM client writes after `api.reload()` (and with `api.publishDefinitions()`) only when the registry really changed. Nothing recomputes per render: `previewCraft` and the rest read the loaded registry directly.
- **Previews.** A player's `previewCraft` is MECHANICAL (`planCraft({ mechanical: true })`): slot validity, tier floors, quantities, the station and its fee, `days`, the materials used. A material's effect is shown only if the character has learned it for that recipe (their Compendium's Experiments, the party's, or the formula's baseline); otherwise the slot is valid and its effect is `{ known: false }`. The GM checks the effects when the craft is queued. The plan carries no result name, output, craft level or loss chance. The GM's own `previewCraft` is unchanged (the full plan).
- **Queue rows, project info and chat (Stage 10d).** `api.queue.list()` and `api.projectInfo()` take the viewer: a GM gets the DC, the odds and the expected days; a player gets a plain row (skill, days, progress current/needed) and no `info` computed at all. A project a relay hands a player has no `dc`. The research summary is a whisper to the owners and the GM with degree words only; the totals and the DC go in a separate GM-only whisper. `api.audit.scan/accept/ledger` are GM-only. Direct GM tools (`api.gather`, `api.craft`, a direct commission craft) roll without PF2e's own card by default (it shows the DC); pass `rollCard: true` to post one.
- **Not fixable (honor system).** Data Foundry stores on an actor, a token or a world setting is delivered to every client that can read it: a project's stored `dc` and `threshold` in the actor flag `projects`, a node token's `perceptionDC` and `ladder`, the GM-written settings. The module no longer hands any of it over in a return value, row or message, but a player's console can still read what Foundry sends their client.
- **Messages.** A character that does not hold a formula: "`<name>` does not know this formula." (whether or not the recipe exists). Held but the recipe exists nowhere (the GM says so): "holds an orphaned formula for this ...". Not loaded yet / no GM: "Your recipes are still loading ..." / "The GM isn't connected ...". An explore submit for a region not in play: refused plainly after one fresh ask to the GM. Anything a player client cannot check is relayed to the GM, whose validation is authoritative (craft, gather, share, build, upgrade and design all already are).
- **GM clients are unchanged**: they still load every pack, and `api.definitions.refresh()` on a GM returns at once.

## The Downtime Hub and the GM log (Stage 11a, v0.18.0)

- `scripts/hub/`: `viewmodels.js` (every rule, pure), `strings.js` (every word), `render.js` (pure HTML), `facts.js` (the only Foundry-bound reader, through the player APIs), `live.js` (what redraws the window), `app.js` (the ApplicationV2 window, built lazily), `entry.js` (scene button and sheet header button). Client settings `hubWindow` and `hubDisplay` hold a player's size and display choices.
- No chat message carries a DC or a roll total. Those go to `scripts/gm-log.js` (memory only, GM client), read with `api.gm.log()` (GM only).

## Research and Compendium tabs, and leads (Stage 11b round, v0.19.0)

- **Research tab** (`viewmodels-research.js`): the character's active projects (read ONLY through `api.projectInfo`, never the raw project flag), step boxes up to `HUB.research.maxStepBoxes` (20), a bar beyond, always "Progress n of m". Roll-with skills show the character's own modifier, never odds. Days are a stepper clamped to [1, free]; Queue N checks submits ONE `research` queue item (`daysReserved` = N). The check log shows degree words and the progress change only: a GM's free-text note is dropped in `facts.js`, before any view-model sees it. Hints are filtered with `safeText` (`DIFFICULTY_WORDS`). **Put the project aside** (formulae only) has a confirm step ("Put aside? Progress is not kept.", Keep gets the focus); it is off while checks are queued, and station-upgrade and design projects are queueable but have no Put aside here. No pace line: any expected figure would need the DC.
- **Leads.** Actor flag `leads` (`LIVE_SCHEMAS.lead`: `id, recipeId, name, note, at`), watched by the Hub. `api.research.giveLead(actor, recipeId, note)` is GM only (note up to `HUB.research.leadNoteMax`; refuses unknown, already-known, already-researching and duplicate leads). The player's **Start researching** calls `api.research.follow(actor, leadId)`, relayed to the GM client by the guarded `researchFollow` handler (7 handlers in all). The GM-client handler refuses, with a plain reason as data: a sender who does not own the actor, a lead that is not on the actor, a lead already used ("The lead is already used up."), a recipe that no longer exists.
- **The sender rule (`senderOf`, `scripts/queue/common.js`).** A relayed handler takes the sender from the socket's own `socketdata.userId`. A `userId` inside the payload is accepted ONLY when it equals the local GM's id (a GM calling on their own client). Never trust a client-supplied id.
- **Compendium tab** (`viewmodels-compendium.js`): Materials, Creatures, Regions, Experiments; only what the character has experienced (no "???"). Sharing is **Only you / Queued / Shared**, worked out by comparing the character's entry to the shared book; Share queues a `share` item for the GM, Cancel removes it. A rejected share cannot be told apart from a cancel or a force-end (all just remove the queue row), so the Hub shows NO "Not shared" line: the entry simply goes back to "Only you".
- Focus: auto-selecting the only project moves no focus; Open in Research, Put aside, Keep and Start researching each set a one-shot focus request (`#wantFocus`) consumed on the next draw.

### Hub actions and Foundry's update echo; queue chat (v0.19.1)

- A player's write is relayed to the GM client. The player's own copy of the actor changes when the server's update ARRIVES (the `updateActor` echo), which can be before or after the relay's reply. So a Hub action (1) sets its result line when the reply arrives (the relay answers in tens of milliseconds in a real window; the line clears itself after `HUB.statusMs`, about 10 seconds, by design); (2) never clears a "queued" line on the echo of its own write (the line clears only when the action later leaves the queue after having been seen there); (3) asks for focus with `#requestFocus(key)`, which waits for the first draw that HAS the control (up to `HUB.focusWaitMs`, cancelled by the person's own click or Tab; the key `window` is the Hub root). The strict fake delivers this echo: `enableEcho` in `tests/fake-world.js`, used by `tests/hub-echo.test.js`.
- **Queue chat (v0.19.2).** EVERY `reject` note (the GM queue window's Reject has chat on by default) is a whisper to the character's owners and the GM, never public: its text names private things (a research project, a blueprint, a patron, a region, a discovery). Craft, gather and commission craft summaries are public by design; research, explore, build and share results are whispers or the GM log. No gather message carries a node charge count ("The node is now depleted." is still said).

## The discovery chain, item classes and the Discovery tracks window (Stage 11c, v0.20.0)

- **Data** (`scripts/data/schemas.js`). `tag` (a theme: name, theme, worksWith) and `note` (a Foundry item flag `note`, points at a formula) are new definition kinds. A material gains `tag`, `classEffects` (role values per item class), an optional `research` track and a gold `value` (defaults by tier at load). A recipe gains `family`, `version`, `requiresTag`/`requiresCount` and its own `research` track. A **track** is `{ milestones: [{ steps, grants: { type: "properties" } | { type: "formula", recipeId } }] }`: steps strictly increase, one properties milestone, at most `DISCOVERY.maxMilestones`. Defaults the editor offers: 4 = properties, 8 = a formula (`DISCOVERY.defaultTrack`).
- **Effects.** Recipe override > the material's `classEffects[recipe.category]` > its general `effects` (the one resolver). The Compendium book gains `classes: { [category]: { [materialId]: { effects: {role: value}, ... } } }`; a successful craft writes the class fact, or a per-recipe fact where the recipe overrides that material. `effectKnown(books, recipe, slot, material)` checks the recipe's own fact, then the class (unless the player copy's `overrideSlots` lists the pair), then the baseline. An experiment share carries the class facts of its category. Older per-recipe facts are folded into classes once at GM startup (`compendium.migrateClasses`, idempotent) and stay as they were.
- **The ledger** (actor flag `discoveries`, watched by the Hub): per studied item `{ key, steps, reached: [{ index, type, recipeId? }], stage 0..2, status, paused? }`. It holds NO thresholds: they are read from the GM's definitions (and the overlay) at each check, so editing a track applies to studies already running.
- **Leads.** From carried items (derived live from the inventory, never stored; `api.research.leadsFor`), stored GM leads, and stored `source: "version"` leads written by the GM (`refreshVersionLeads`) when a higher version's previous formula is known and enough distinct tagged materials are understood. `api.research.follow(actor, leadId)` handles all three; the GM client checks the inventory itself. A study is an ordinary `research` queue item with the project id `study:<kind>:<id>`; its rows carry no counts. **Put aside** on a study pauses it and keeps its progress.
- **Crafting gate.** `previewCraft` (player and GM) and so `craft` and the queue refuse a tracked material the character has not studied, with a plain sentence first in the list. Properties are open when the item has no track, the properties milestone is reached, or the character has already crafted with it.
- **Relay** (`stripForPlayer`): no `effects`, `classEffects`, `research`, `family`, `version`, `requiresTag`, `requiresCount`; a material gets `hasTrack` (yes/no, overlay included) and its `tag` only when the character knows it; the `tag` definition and held `note` definitions are sent; a recipe gets `overrideSlots` (no values). `value` is sent for materials the character owns. Facts include `notes` and `studied`, and `discoveries` is watched, so a milestone refreshes the copy.
- **The Discovery tracks window** (0.20.0, replaced by the Item editor in 0.21.0): its track rows, validation and the `discoveryTracks` overlay now live in the editor (`scripts/editor/rows.js`); `api.discovery.tracks.*` still reads and writes the overlay.
- **Flag updates merge** (v0.20.1): an object written to an actor flag is merged into the stored one, so a key left out survives. Resuming a put-aside study writes `paused: false`. The test fake merges the same way.
- **The Discovery tracks window layout** (v0.20.1, carried into the Item editor): list left, search and filter chips, collapsible groups with counts, Save/Discard outside the scrolling part, fields styled like the Hub.
- **Hub leftovers.** Each action's failure says what it was trying to do. A relayed action is guarded from its first click, looks busy only after `HUB.busyShowMs`, and after `HUB.noAnswerMs` the Hub says "The GM didn't answer, try again" and frees the button (a late answer still shows its result).

## The Item editor, the Material creator and the effect builder (Stage 11d, v0.21.0)

GM only. `docs/11d-item-editor-addendum.md` records the decisions; `docs/20-stage11d-gate.md` is the real-Foundry gate.

- **Where content lives.** The editor writes the world setting `editorDefinitions` (`{ v: 1, records: { "<kind>:<id>": { kind, id, mode: "new" | "patch", fields } } }`), never the packs. A `new` record is a definition made in the editor; a `patch` is an edit of a pack definition (only the changed fields; removing a field restores the pack's value). `scripts/editor/layer.js` layers the records over the packs' SOURCE TEXT before validation, so an editor record goes through exactly the validation a pack page does and a bad one is reported by name and skipped. `reload` keeps the raw pages in `api.baseSources`; every editor change rebuilds the registry in memory (`scripts/editor/build.js`), and is REFUSED (nothing written) if it would add a definition error. A saved edit that matches nothing (its pack item is gone) is a **leftover**, listed in the window and removable; so is a research track in the old overlay whose item is gone. Definitions that exist only in memory (a test fixture) are kept across a rebuild and cannot be edited (`api.editor.canEdit`).
- **Items.** Creating a material or a note also creates a linked WORLD Item (flag `template: true`) in a Materials / Notes folder; `giveMaterial` and `giveNote` use the same builder (`newItemData`), so a copy carries the definition's name, image, description, bulk and price (gold value is also the PF2e price). **Push to copies** (`api.editor.pushCopies`) writes those fields onto every existing copy (world items and every actor's); copies on unlinked scene tokens are counted and skipped, and the window says so.
- **Effect builder.** A material's `effectBlocks` (`{ general, byClass }`, each a set of `{ power?, blocks, extra? }`) is the source; the blocks COMPILE (`scripts/editor/blocks.js`) to the `effects` / `classEffects` role values the craft engine already applies (Add damage = `bonusDamage`, Grant resistance = `resistance`, Special ability text = `specialAbility`; the power tier = `basePower`, or `spellPower` for a focus). A role holds one value, so one block per type per class. Dice and the resistance amount may be a table by tier (T1 to T5); a material has ONE tier, so the row for its own tier is the one compiled. Per-recipe overrides are written on the material (`recipeOverrides`) and copied onto that recipe's override list by the layer. The classes are `ITEM_CLASSES` (weapon, bomb, consumable, armor, robes, focus, trinket), each with when its effects apply. The plain-words line comes from the Hub's own wording (`effectLines`), so the preview is what the Hub says.
- **Changing what players may know.** `api.editor.update` refuses (with `details.needsConfirm` and who knows) a change to a material's tag, its effects, or a tag's theme when a character's Compendium (or the shared one) already knows the material, until it is called with `confirmed: true`. The window asks in plain words.
- **Delete / retire / revert.** A pack item can only be retired; an editor-made item can be deleted only when nothing uses it (copies, recipe overrides, node ladders, creature yields); the refusal says where. Revert takes back a patch (one field or all).
- **Export / import.** `api.editor.exportRecords` / `importRecords`: a plain JSON bundle (`format: "pathfinder-progress-editor"`); clashes are skipped with a reason unless `replace`; a bundle that would break a definition imports nothing.
- **Players.** `stripForPlayer` drops every editor field (`img`, `description`, `bulk`, `label`, `retired`, `effectBlocks`, `recipeOverrides`) from a material; a note still travels as id, name and `hasTrack`. The editor and its api refuse a player.
- **The window** (`scripts/editor/{model,app,entry,rows}.js`): list left (search, filter chips, collapsible groups, Leftovers), editor in the middle (Basics, Discovery, Research track, Effects), "What players see" on the right with an item-class picker (it opens on the first class that has effects). Save is on only when something changed and nothing is wrong, and the reason sits beside it. Typing in a text box refreshes only the preview and the action row (a full redraw between a field losing focus and the click that caused it would replace the button under the pointer). A question (players may know, push, revert, delete) appears beside the buttons and puts focus on the safe answer. Opens from the scene controls (screwdriver-and-wrench) and from a material or note item sheet's header; `api.discovery.openEditor(key)` too.

**Item editor, v0.21.1.**
- **The preview has three stages** (`scripts/editor/preview.js`): *Just picked up* (name, tier, worth, bulk; the tag and theme only for an item with NO research track), *After studying* (what the properties milestone adds; with no study it says "No study: known on pickup." instead of repeating stage one) and *After a successful craft in this class* (the effect lines for the picked class). Each stage is built from `stripForPlayer` (what a player's client is sent) and the Hub's own Compendium view-model (`compendiumTab`, `materialInfoFor` shared with `facts.js`, and the class fact a craft writes), never the raw record, so it cannot say what the Hub would not: no effect before the craft stage, and no step count, threshold or DC at any stage.
- **Narrow layout = one scrolling column** (below `HUB.stackBelowPx`): the window scrolls, every pane takes its natural height, only the list keeps a capped box with its own scroll, and its chips wrap inside the pane. The layout harness now draws narrow editor windows at a fixed tall AND short height and checks the editor pane's height, that the filter row stays inside its pane, and that no control overlaps another (the 0.21.0 matrix drew narrow windows with an auto height and exempted scrolling boxes, so a squeezed pane passed).
- **Required choices start on a disabled placeholder** ("Choose a formula", "Choose a tier", "Choose a kind of note"), Create stays off and a reason line says why. A checkbox is a normal-sized box inside a label row; the label row is the 44px target.
- A tag created in the editor carries only its own fields; deleting a tag a material still names is refused.

**Checkboxes and radios, v0.21.2.** Foundry restyles them (a dark fill when unchecked, ticks drawn with `::before`/`::after`), so `styles/hub.css` resets every `input[type=checkbox|radio]` under `.pfp-hub` (marked `>>> checkbox reset`) and draws one tick of its own; unchecked = empty bordered box, checked = box with one tick. The layout harness imitates Foundry's checkbox styling and reads both states from the computed style (pseudo-elements included); a mutation test strips the reset and must fail.

## Offline queue (players submit any time)
Sockets only reach online clients, so the queue lives in data players can write:
1. Each player's actor has a `pendingActions` flag.
2. Days are **reserved at submission** (cannot over-book).
3. On GM login, the module scans all actors and lists pending actions.
4. **GM reviews first**: a GM window lists pending actions with "Resolve all" plus edit/reject per row. Resolution runs in submission order via the GM client.
5. Resolving an expedition **prepares** the scene only; the GM launches it.
6. Commissions are two queued steps in player-to-player flow (patron submits, crafter accepts).
7. Players receive a results summary per resolved action.

## UI surfaces
**Player: Downtime Hub** (standalone ApplicationV2 window, opened from a button; optionally a header button on the PF2e sheet later). Tabs: Research, Explore, Commissions, Workshop, Formulas. Shows day budget and queue.

**Keyboard (any window we build).** Foundry's KeyboardManager cancels Tab (its "cycle view" binding) and similar keys before the browser can move focus, so inside an ApplicationV2 window Tab does nothing and Space scrolls the page behind it. Every ApplicationV2 window we build must stop Tab, Enter and Space from bubbling out of its root (never `preventDefault`: the browser still moves focus and presses the button), only for events that came from inside the window, once per frame, removed on close, and give the root `tabindex="-1"` so a click on blank space focuses the window rather than the page. The Hub does this in one place (`scripts/hub/app.js`, `HUB.keysKeptInside`); Escape and other keys stay untouched. The strict test fake cannot reproduce Foundry's own handler, so the proof is the gate (`docs/17`, Step 38).

**Gather dialog**: opened by clicking a node token in the scene; small dialog for skill choice and roll.

**GM tools**
- Review queue window (see above).
- Commission creator form: patron name, item, `materialsFrom`, payout, `teaches`.
- Definitions are edited directly in the compendium packs (no custom editor).
- GM-only "Save to compendium" button on crafted item sheets.
- Anchor placement: GM drops hidden node tokens on scenes.

## Tokens
Nodes (anchors, active nodes, corpses) are tokens with flags. Hidden tokens are anchors; activation unhides them. Filter node tokens from the combat tracker and token lists.

## Effects that act on a target (Stage 11d, v0.22.0)

A crafted weapon, bomb or consumable whose materials carry "Apply a condition" effects offers them to the GM when it hits or is used. Decisions: `docs/11d-item-editor-addendum.md` ("v0.22.0 decisions"); PF2e 8.6.1's message shapes: `docs/probes/11d-targets-probe.md` (Results); the real-Foundry gate: `docs/21-stage11d-effects-gate.md`.

- **One adapter file for PF2e's shapes**: `scripts/adapter/pf2e-effects.js` reads an attack roll (`flags.pf2e.context`, `context.target` = the FIRST target only), ignores a damage roll, takes the first consumable card (origin type consumable, no context), finds the item through `context.origin.token`'s actor first (an unlinked token's synthetic actor; `origin.uuid` names the world actor's item), reads the roller's targets from `message.author.targets` on the GM client, rolls a save with `token.actor.saves[type].check.roll({ dc, skipDialog, createMessage: false })` and puts a condition on `token.actor` (`increaseCondition` ADDS, so only the difference to the wanted value is added, with a cap; never the world actor). A message it cannot read becomes `kind: "other"`, which becomes the fallback card.
- **Pure logic in `scripts/effects/`**: `resolve.js` (the effects of a crafted item, looked up again from its `crafted` flag through the ONE resolver; `decide` = card / fallback / skip per item class), `card.js` (the whisper: plain words, ids only in the flag), `apply.js` (DC = `levelDC(recipe.craftLevel)`, one secret save per effect per target, critical failure = value + 1 capped at 4, success nothing, "No save" applies by itself; DC, total and degree go to `api.gm.log`, never to chat), `plain.js` (plain words, `forPlayer`, the leak scan), `hook.js` (the active GM's `createChatMessage` reaction, dedupe by message id and, for a consumable, by `origin.uuid` for `EFFECTS.dedupeMs`; the card's buttons are disabled while a roll is in flight). `main.js` has one `installEffectsHooks` line and `api.effects` (GM only: `handle`, `applyCard(id, { forceDegree })`, `skipCard`).
- **Nothing GM-only on the item or in a message**: the crafted item carries only the `crafted` flag (recipe and materials); the condition, value, save and DC are looked up on the GM's client when Apply is pressed. The item description gets the plain line at craft; `forPlayer(role, value)` turns `applyCondition` into `{ plain: [...] }` before the Compendium book is written (a class fact, a per-recipe fact and a formula's baseline).
- **The role** `applyCondition` is an array (several per class) and exists only for weapon, bomb and consumable. A recipe slot must list it in `drives` to use it.
